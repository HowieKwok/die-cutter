# 五金模切 帧队列与 PLC 发布 — 实施改造方案

> 本文只描述**改什么、改成什么形态、按什么顺序验收**，不含代码。
> 目标形态的逻辑依据见 `docs/五金模切_帧队列与PLC发布设计.md`。
> **范围：仅五金模切。** 激光模切的流程、判定、发布、界面一律不动。

## 0. 交付边界

| 项 | 约束 |
|---|---|
| 业务范围 | 只改 `MaterialCrafEnum.五金模切` 分支 |
| 共享代码 | `DieCutJudge`（激光/五金共用判定）只读使用，不改语义 |
| 共享界面 | `Form_Simulation`、`UC_ToolView` 是两机型共用，必须按机型判定后再改外观 |
| 相机 SDK | `CameraHKControl` 的 `GrabCount` 不再作为业务帧号来源；不改 SDK 采集行为 |
| 数据格式 | 不改 PLC 点位表与符号名，仍为 3 个结果点 + 心跳 + 3 个多次NG |

## 1. 现状 → 目标 差异

| 能力 | 现状 | 目标 |
|---|---|---|
| 帧号 | 两套计数：相机 `GrabCount` + 流程 `nCurProImgId` | 工位级唯一序号，单一来源 |
| 线扫队列 | 有队列，出队在处理开始 | 保留（策略不变） |
| 线扫帧号校验 | 合片时用产品ID比较，事后 | 处理前校验，不一致即丢帧并钳位 |
| 尺寸 | 3 路各自判 + 按空字符串 `SN` 等齐 | 3 槽合并，按帧号校验，无帧队列（已确认） |
| PLC 发布 | 视觉线程内同步直写点位 | 结果队列 + 独立发布通道 |
| 失败处理 | 只累加失败计数 | 300ms×3 → 暂停 + 非模态提示 |
| 待检 3 | 帧开始直写 | 与结论成对入队 |
| 仿真界面 | 两列滚动日志 | 两工位 Tab + 队列/发布状态 |
| 仿真节拍 | 所有相机同一节拍 | 上线 0 / 下线 +500ms / 尺寸 +2500ms |
| 自动模式 | 需要点启动 | 无启停按钮，帧触发即处理 |

## 2. 模块划分

| 模块 | 形态 | 职责 | 不负责 |
|---|---|---|---|
| `五金模切LineScanParam` | 新增，`: DieCutParam` | 覆写入队：去抖 → 取号 → 校验 → 入队 | 帧号算法、判定 |
| `五金模切SizeParam` | 新增，`: SizeDetectParam` | 同上，走尺寸组窗口取号 | 帧号算法、判定 |
| `StationFrameSequencer` | 新增，线扫/尺寸各一实例 | 分配帧号、校验、钳位、换卷复位 | 取图、判定 |
| `FrameTriggerGate` | 新增，每相机一实例 | 50ms 去抖，返回"接受/丢弃" | 帧号、队列 |
| `LineScanFrameQueue` | 复用现有队列 | 存放待处理帧 | 处理状态、结果 |
| `SizeMergeSlot` | 新增，替换现有等齐组 | 3 槽合并、帧号一致性校验 | 尺寸项判定 |
| `PlcResultQueue` | 新增，3 实例 | 存放待发布结论（含待检） | 点位写、重试 |
| `PlcResultPublisher` | 新增，3 通道 | FIFO 发布、超时重试、暂停/恢复 | 判定、界面 |
| `StationStatusBoard` | 新增 | 只读状态快照供 UI | 任何写操作 |
| `NonModalAlert` | 新增，单例 | 非模态提示、去重 | 阻塞调用方 |
| `SimTriggerOrchestrator` | 新增（仅仿真） | 一产品节拍按偏移触发各相机 | 视觉、判定 |

依赖方向：`视觉流程 → 结果队列 → 发布通道 → PLC`。
反向不存在：PLC 与界面都**不能**回调视觉流程。

## 3. 帧号与去抖

### 3.1 分配点

- 在**图像入队**这一步分配并校验。五金落点是 `五金模切LineScanParam` /
  `五金模切SizeParam` 覆写的 `CallBackImgDataDeal`；基类 `BaseProParam` 不动。
- 删除该处对 `nCurProImgId` 的使用；同样不再把 `GrabCount` 或 `GrabCount+1` 写进业务帧号。
- **待检值 3 也在这一刻投递**（分配帧号后立刻入结果队列），
  相机帧开始回调（`RaiseCamCallbackStart`）不再承担任何投递/写入职责。
- 理由一：触发回调与图像回调是两条路径，用触发侧的预测值当 ID，丢一张图就永久错位。
- 理由二：帧开始回调早于图像回调，此刻还没有帧号，无法与结论配对；
  在帧开始直写 3 还会让去抖丢弃的重复触发多写一次待检。

### 3.2 线扫序号

```text
UpSeq    : 上线扫已接受帧数（下次分配值）
DownSeq  : 下线扫已接受帧数
Expected = UpSeq - 1
Actual   = DownSeq
```

| 情形 | 动作 |
|---|---|
| `Actual == Expected` | 正常：分配 `Expected`，`DownSeq` 保持 |
| `Actual != Expected` | 丢帧（不入队、不处理、不写 PLC、不占号）；`DownSeq = Expected`；非模态提示 |

> 钳位后，滞后/超前那一帧对应的产品在下线侧**没有视觉结论**。
> **已定（决策 14）**：钳位时补一条 NG 结果入下线结果队列，保证 PLC 每片必有一拍。
>
> **换卷例外（必须实现）**：换卷把序号归 1 后，下线首帧的 `Expected` 会算成 0，
> 而 0 是"尚未有产品"的非法帧号。因此换卷完成标志置位后，**下线第一帧无条件放行**，
> 不参与比较，放行后立即恢复常规校验。否则换卷后第一片必被丢弃。

### 3.3 尺寸序号

- 尺寸工位一个序号发生器，**按组窗口分配，不按相机分配**。
- 分配点在 `CallBackImgDataDeal`：窗口空闲时第一路触发 → 取 `NextSizeSeq` 开窗；
  窗口内的其余两路**复用同号**；窗口超时（`SizeStationTimeout`，默认 1500ms）后重新开窗取号。
- 合并槽只**校验** `ExpectedFrameId`，不负责分配。
  若把分配放进合并槽（由第一路完成者决定），三路必然同号，"帧号不一致"永远检测不出来。
- "三路各取各号"与"第一路完成者决定"两种写法在此明确排除。

### 3.4 50ms 去抖

```text
每相机一个 LastAcceptedTicks
触发进入 → now - LastAcceptedTicks < 50ms ?
   是 → 丢弃本次触发（不入队、不占号、不提示）
   否 → LastAcceptedTicks = now，继续入队/编号
```

- 必须放在**图像入队前**，否则图仍会进队列，帧号与图数量再次分叉。
- 丢弃属于正常抖动，不提示、不计异常。
- 尺寸工位同样需要：多出的一帧会让合并组变成 4 路。

### 3.5 复位时机

| 事件 | 行为 |
|---|---|
| 停止 → 启动 | **不重置**帧号 |
| 换卷（`StartFilmRoll`） | 重置所有序号为 1，同时清空抖动时间戳；置"下线首帧放行"标志，下线下一帧不校验 |
| 复位/清数据 | 清空队列与合并槽；帧号按换卷规则处理（同换卷则一并重置） |

### 3.6 帧结算与代际

**帧结算**

- 每台相机维护"已入队未结算"计数：入队 +1，结算 -1，稳态应回落到 0。
- 结算必须有**统一出口**（流程 finally），覆盖：正常判完、裁图失败、未产出 EA、
  EA 判定异常、流程抛异常。
- 异常一律结算为 NG。**禁止无结论**：结果队列少一条，PLC 就少一拍，
  外部表现是机构停在等结果。
- 未产出 EA 也算一次结算：不能因为"没有 EA 产品"就不回传。

**代际号**

- 停机、换卷、复位各自增一次 `Generation`。
- 帧在入队时记录当时的代际号；结果入队前校验：
  `仍在运行 && frame.Generation == 当前代际`，不满足直接丢弃。
- 目的：清空队列并写 0 之后，不会被"停机瞬间已出队、随后才判完"的迟到结果覆盖。
- 换卷时帧号归 1，但旧代际的帧一律丢弃，避免旧帧号污染新队列。

## 4. 线扫工位改造点

### 4.1 图像入队（五金专属 Param 子类覆写）

**隔离方式：不改共享基类，改用子类覆写。**

| 位置 | 现状 | 改为 |
|---|---|---|
| `BaseProParam` / `DieCutParam` | 激光与五金共用 | **一行不改** |
| 新增 `五金模切LineScanParam : DieCutParam` | — | 只覆写 `CallBackImgDataDeal` |
| 新增 `五金模切SizeParam : SizeDetectParam` | — | 只覆写 `CallBackImgDataDeal` |
| `五金模切Profile.BuildCamSlots()` | 创建基类实例 | 改为创建上述两个子类 |

选择子类覆写的理由（已核实 `CallBackImgDataDeal` 是 `virtual`）：
- `五金模切Profile.BuildCamSlots()` 是**五金专属工厂**，激光走 `LaserDieCuttingProfile`。
  子类只可能由五金工厂创建，**激光那份代码里编译期就不存在五金分支**。
- 若改用 `CraftType` 运行时分支，等于把五金行为塞进激光的执行路径，
  回归只能靠人测；子类覆写则不需要为"激光是否被改到"做额外验证。

覆写体内的步骤：

1. 进入后先过 `FrameTriggerGate`：50ms 内重复 → 直接丢弃并返回。
2. 通过后向 `StationFrameSequencer` 申请帧号：上线按下发号、下线按 `Up-1` 校验，
   尺寸走组窗口（同组三路复用同号，见 3.3）；三者的分支都在同一处收敛。
3. 校验不通过（下线超前/滞后）→ 丢弃、提示、钳位；图不进入任何队列。
4. 通过 → `alreadyDealGrabImage.Enqueue(...)`，`image_ID` 写为申请到的帧号。
5. 子类**不读不写** `nCurProImgId`；基类字段原样保留，激光继续用它。

> 运行时行为仍是"同一份入队语义"，区别只在代码归属：五金走子类，
> 激光走基类。两者共享的是 `alreadyDealGrabImage` 这个数据结构，不是这段逻辑。

### 4.2 裁图流程（`RunCropProcess`）

- 出队点保持"取队首"不变，帧号直接取 `InfoImgInfo.image_ID`。
- `imageEAInfos` 目前是裸 `List`，被裁图线程 `Add`、EA 线程 `[0]/RemoveAt(0)` 同时访问。
  **必须改为线程安全容器**（队列或加锁的列表），这是本次改造的强制项。
- 拼接、标定、EA 生成逻辑不变。

### 4.3 极片 EA 流程（`RunEaProcess`）

- 取帧方式随 4.2 的容器一起调整。
- 帧号、产品号仍传入 `ShowHalconWindow`，但产品号不再兼任帧号。

### 4.4 判定结束（`Server_五金模切.ProcessEaImage`）

- 判定完成后**不再直接写 PLC**，改为：
  ```text
  PlcResultQueue[上线/下线].Enqueue { FrameId, Value = OK/NG }
  ```
- 写 CSV、统计、界面队列保持原样，但**回传日志/界面行要跟随发布语义**：
  现在它们挂在"写 PLC"之后，直写删除后必须移到"入队"或"发布成功"处，并标明状态。
- `MergeOnce`（A/B 合片）**改为按帧号相等配对**，`FrontSideCount/BackSideCount` 退出：
  `EAID` 只做显示，不参与配对（裁图流程里 `nEAId` 有多个自增分支，与帧号不是一一对应）。
- 帧号必须从裁图帧一路带到 EA 产品：`EAImageInfo` / `DieCutEAProduct` 增加帧号字段。
- 合片只服务统计与界面，**PLC 结果按线别各自发布，不依赖合片**。
- `Station1_Product` 在五金没有消费者（只入队、只清空），随合片改造一并删除。

### 4.5 PLC 侧（`Server_五金模切.PLC结果.cs` / `工位信号.cs`）

- `OnUpFrameStart` / `OnDownFrameStart`：**不再投递待检**。待检改在 4.1 分配帧号时投递。
  帧开始回调只保留"运行态检查"等既有语义。
- `WriteAppearanceResult` / `WriteSizeResult` 从视觉可调用的入口移除（或改为私有）。
- `WriteRaw` 的全局 `PlcWriteLock` **收敛为"每 PLC 一个写调度器（单写线程）"**，
  不再按点位拆锁：结果三通道只提单，由调度器串行写入，心跳最高优先。
  理由：拆分点位锁会导致三条线程并发写同一连接、报文交错；共用一把长锁又会让一次写超时
  饿死心跳。串行调度是唯一同时满足两者的形态（与 6.2 一致）。
- 发布通道的重试**不得计入** `PLCCommunicationBase.WriteFailCount`：
  该计数 `> WriteFailNum(2)` 会触发"发送数据失败次数过多"的**停机报警**，
  与"3 次失败只提示、不停机"的决策冲突。
- 结果入队前校验 `Is_Run` 与代际号（见 3.6），替代原来直写入口里的 `Is_Run` 判断。

## 5. 尺寸工位改造点

### 5.1 无帧队列（已确认）

> 原始需求是"每个相机都有帧队列"。尺寸工位不建队列，合并槽本身即为 3 槽缓冲，
> 同时承担帧号校验。该偏差已由用户确认接受，按本方案实现。

- 三路相机仍各自触发、各自进 `alreadyDealGrabImage`（SDK 行为，不可避免），
  但业务侧**不再为尺寸建立额外的帧队列**，也不做跨帧缓冲。
- 50ms 去抖在入队前生效，保证一个产品周期每路最多一帧。

### 5.2 合并槽（替换现有等齐组）

```text
SizeMergeSlot {
    ExpectedFrameId
    Slot[cam1..cam3]
    CreatedAt
}
```

| 事件 | 行为 |
|---|---|
| 组空闲 + 某路完成 | 开槽，`ExpectedFrameId = 该帧在入队时拿到的组帧号`，入槽 |
| 其余路完成且帧号相等 | 入槽 |
| 其余路完成但帧号不等 | **不入槽**，非模态提示，该帧结果丢弃 |
| 窗口超时后才到 | 视为下一组，重新开窗取号，并提示上一组缺帧 |
| 三槽齐 | 合并判 OK/NG → 结果入尺寸结果队列 |
| 超时未齐 | 按 NG 结案 → 入队；提示 |

改动要点：
- 合并键从 `product.SN`（当前恒为空字符串）改为 `ExpectedFrameId`。
- `_sizeAllReadyEvent` 由全局单例改为"每组合一个信号"或"尺寸工位串行只允许一组"，
  避免多组并存时互相唤醒。
- 等待方仍是 `occurrence == 0`，另两路只提交。
- 结果来源改为结果队列，删除 `WriteSizeResult` 直接写点位。

## 6. PLC 结果发布

### 6.1 队列元素

```text
ResultItem {
    FrameId
    Kind      : Pending | Ok | Ng
    Value     : 3 / 1 / 2
    Attempts  : 0..3
    CreatedAt
}
```

### 6.2 三条通道

| 通道 | 队列 | 点位 |
|---|---|---|
| 上线 | UpResultQueue | `CCD_DATA_RD.LineScan_Up` |
| 下线 | DownResultQueue | `CCD_DATA_RD.LineScan_Down` |
| 尺寸 | SizeResultQueue | `CCD_DATA_RD.Size` |

- 三条通道**只独立队列与状态机**，不各开 socket：五金只有一个 `Server_五金模切PLC` 实例。
- 写动作统一交给**每 PLC 一个写调度器（单写线程）**串行执行：心跳优先，结果通道轮流取队首。
  这样既有 FIFO 与独立重试，又不会让三条线程并发写同一连接。
- 只取**队首**；成功才移除；失败留在队首。
- 同一帧的 `Pending` 与 `Result` 必须**成对入队**，顺序固定。

### 6.3 状态机

```text
Idle ──有元素──▶ Sending
Sending ──写入成功──▶ Idle（移除队首）
Sending ──超时/失败──▶ Attempts++
Attempts < 3 ──▶ 稍后重试 Sending
Attempts = 3 ──▶ Paused（队首保留，停止后续发布，非模态提示）
Paused ──操作员确认──▶ Attempts=0，回到 Idle
```

### 6.4 写超时（前置未验证项；原 2000ms 收紧为 300ms）

- 判定依据是"写入调用是否在 `ResultWriteTimeoutMs`（默认 **300ms**）内完成并返回成功"。
- **为什么不是 2000ms**：心跳周期 1s，单次写阻塞 2000ms 会跨过两个心跳周期；
  "心跳优先"只在取下一个任务时生效，救不了正在阻塞的那次调用，PLC 必然判通讯断开。
  300ms × 3 次合计 ≤900ms，仍在一个产品节拍内，不影响保序。
- 现状：`PLCCommunicationBase.Write` 是**同步 void**，没有超时参数；
  底层 HslCommunication 只能通过 `ReceiveTimeOut / ConnectTimeOut`（整实例生效）限制等待。
- **实测结果（2026-11-24，已完成）**：`OmronCipNet`，代码中这两个属性**从未被赋值**，取库默认值。

| 场景 | 单次 `Write` 阻塞 | 说明 |
|---|---|---|
| `ReceiveTimeOut/ConnectTimeOut` 默认（5000/10000） | **5014ms** | 连上但对端不回（PLC 死机/流程卡死） |
| 同上，端口拒绝 | **2046ms** | 内部含一次重连重试，仍 >2s |
| 两属性都设为 **300ms** | **313ms** | 返回 `IsSuccess=false`，阻塞被正确限制 |

- **结论：300ms 判定成立，且不需要新增包装重载。**
  只要把 `ReceiveTimeOut`/`ConnectTimeOut` 调到 300ms，同步 `Write` 自己就会在 ~313ms 返回。
  这比 `Task.Run + Wait(300)` 更安全——后者放弃写之后线程仍会在底层阻塞最多 5s 并占用 socket。
- 因此第 6 步不再需要"带超时的写重载"，改为：连接时设置两个超时属性 + 失败计数隔离。
- 注意事项：
  1. `ReceiveTimeOut` 同时作用于**读**。读点位若因 300ms 超时反复失败，会累加 `ReadFailCount`
     并触发"读取数据失败次数过多"停机报警，需一并评估（读路径建议单独放宽或复用同一口径）。
  2. `ConnectTimeOut=300` 对健康局域网足够（TCP 握手 <1ms），但 PLC 冷启动慢时会拖慢首次连接，
     可设为 1000ms，稳态写路径仍由 `ReceiveTimeOut` 兜底。
- **超时后的硬约束**：被放弃的那次写可能仍在底层执行，此时直接发下一条会在同一 socket
  上穿插报文。因此超时必须同时**判定连接不可用并断开重连**（或等待该次写真正返回），
  确认无在途写之后才允许重新发布。
- 超时与"返回失败"等价处理（计入本通道的 3 次重试）。

### 6.5 非模态提示

- 提示窗 `Show()` 而非 `ShowDialog()`，不阻塞任何调用方。
- 同一通道的同类提示**去重**：已有一个未关闭的提示时不再叠加。
- 提示内容：通道名、卡住的帧号、已重试次数、当前队列深度。
- 提供"重试"和"关闭"两个操作；关闭不等于恢复，恢复需显式确认。

### 6.6 队列深度

- 深度阈值（建议 50）超过时在状态栏/状态板提示，不弹窗。
- 深度持续增长说明发布吞吐不足，不是视觉问题。

## 7. 生命周期与并发

### 7.1 启动 / 停止 / 复位 / 换卷

| 事件 | 动作（严格按顺序） |
|---|---|
| 启动 | 启动 3 条发布通道；帧号不重置；代际号不变 |
| 停止 | 停通道 → 清 3 条结果队列 → 清合并槽 → 写 0 → 代际号 +1 |
| 复位 | 同停止，并清空显示队列与统计缓冲 |
| 换卷 | 帧号全部归 1 → 代际号 +1 → 清结果队列与合并槽 → 写 0 |

顺序的理由：先停通道，才不会在清队列时又有一次写入进来；
先加代际号，才能让"已出队但还没判完"的帧在结算时被丢弃。

> 停机时"丢弃未发布结果"是刻意的：继续补发会把停机后的 PLC 状态改回 OK/NG。

### 7.2 读写归属

| 数据 | 唯一写者 | 读者 |
|---|---|---|
| 帧号 | 入队线程（每相机一个） | 全链路只读 |
| 代际号 | 停机/换卷/复位 | 入队与结算校验 |
| 帧队列 | 入队线程写、流程线程取 | 状态板快照 |
| 合并槽 | 三路流程（临界区内） | 等待方 |
| 结果队列 | 各视觉流程 | 对应发布通道 |
| PLC 结果点 | 写调度器（单写线程） | PLC |
| PLC 心跳/多次NG | 通讯线程（各自点位锁） | PLC |
| 状态板 | 各模块发布快照 | UI 定时读取 |

硬约束：
1. **视觉线程与相机回调线程不得写 PLC 点位。**
2. **写动作必须串行，且不按点位拆锁**：结果通道、心跳、多次NG 都只"提交"给每 PLC 一个
   写调度器（单写线程），由它串行写入、心跳最高优先。拆成点位锁会让三条线程并发写同一条
   连接、报文交错；共用一把长锁又会让一次写超时饿死心跳。单写调度器同时满足两者。
3. 合并槽的临界区内不允许做判定、写文件、写 PLC。
4. 停止/复位与发布通道之间必须有通道级互斥，避免"清空后又被写入"。
5. UI 只读状态板，不直接读队列内部结构。

## 8. 仿真改造

### 8.1 触发编排

一个产品节拍，由 `SimTriggerOrchestrator` 统一发令：

| 偏移 | 触发对象 |
|---|---|
| `t0` | 上线扫 |
| `t0 + 500ms` | 下线扫 |
| `t0 + 500ms + 2000ms` | 尺寸 1/2/3（同一时刻，从下线触发起算） |

实现要点：
- 相机不再各自持有独立节拍；改为"工位 + 偏移"参数，由一个节拍源统一驱动。
- 编排器由 `Simulation/SimBootstrap.cs` 在 `BuildCameraFactory` / `TriggerWhen` 处接入：
  `TriggerWhen` 现在只看 `Is_Run`，改造后要叠加"本相机是否轮到自己"。
- `ResolveSpec` 需要额外解析"工位 + 偏移"，`SimCameraSpec` 增加这两个字段。
- 尺寸三路同一 tick 触发，配合工位序号发生器，天然得到同一帧号。
- 保留现有产能调节：改变的是 `t0` 间隔，不是偏移。

### 8.2 界面

`Form_Simulation` 改为两个 Tab，删除滚动日志：

**线扫工位**：上线扫 / 下线扫 两行，列 = 队列帧号、处理中帧号、最近完成帧号、结果队列帧号、发布状态、重试次数、帧号校验状态。

**尺寸工位**：尺寸1/2/3 三行（当前帧号、是否入槽）+ 合并行（期望帧号、x/3、校验结果）+ 发布行（队列帧号、状态、重试次数）。

- 只对五金启用；激光仍用原界面，避免回归。

## 9. 自动模式按钮

- 五金自动模式：隐藏 `btn_run`（启动/停止），不提供人工启停。
- 必须同时补**启动钩子**：`TriggerWhen = () => Project.Instance.Is_Run`，
  不点启动 `Is_Run` 恒为 false，`CallBackImgDataDeal` 会销毁图像而不入队。
  因此五金在"自动 + 非仿真"下，进入主界面后要自动执行一次 `StartRun()`。
- 由于五金点位表**没有自动/停止输入点**，停止只能由复位/换卷/停线等既有入口触发。
- **停机后如何再启动（必须定义，否则现场停一次就再也起不来）**：
  复位完成 → 置"待启动"标志 → 下一次收到 plc在位/自动信号（或操作员在复位流程末尾确认）
  → 自动 `StartRun()`。该钩子与首次进入主界面用的是同一个方法，不要写两套。
- 仿真模式：保留 `btn_run`，仿真需要人为开始；仿真不自动 StartRun。
- 判定条件按机型 + 运行模式，不能只按模式，否则会影响激光。

## 11. 风险与回归清单

| 风险 | 影响 | 处置 |
|---|---|---|
| 帧号钳位会丢片 | 该产品在下线侧无视觉结论 | **已定**：钳位时补一条 NG，PLC 每片必有一拍 |
| 50ms 去抖 = 上限 1200 片/分 | 超过后真实产品会被当重复触发丢弃 | 参数可配置，按实际产能核对 |
| 写超时 | 底层 `Write` 同步且无超时参数 | **已实测**：默认 5014ms，设 300ms 后 313ms，判定成立 |
| 写超时饿死心跳 | 2000ms 单次写 > 1s 心跳周期，通讯被判断开 | 单次写超时收紧到 300ms；不允许改回 2000ms |
| 发布重试触发停机报警 | `WriteFailCount > 2` 会报"发送数据失败次数过多" | 新增带超时重载并隔离计数，或换独立写入口 |
| 全局 PLC 锁 | 一次长写阻塞会饿死心跳与多次NG | 每 PLC 一个单写调度器，心跳最高优先，不按点位拆锁 |
| 超时后仍有在途写 | 同一 socket 穿插报文 | 超时即判连接不可用并重连，确认无在途写再发布 |
| 换卷首帧 | 序号归 1 后 `Expected=0`，下线首片必丢 | 换卷后置标志，下线首帧无条件放行 |
| 单 socket 并发写 | 三通道各开线程会交错报文 | 三通道只独立队列/状态机，写动作串行 |
| 共用基类改动 | 原方案需在 `BaseProParam` 加机型分支，波及激光 | **已消除**：改为五金子类覆写，基类一行不改（见 4.1） |
| 子类覆写漂移 | 子类与基类后续各自演化，入队语义分叉 | 子类只做"取号+校验"，不复制基类的销毁/日志逻辑；基类改动时同步复核 |
| 共享界面改动 | 可能改到激光 | 所有 UI 改动先机型判定 |
| 停机丢弃未发布结果 | PLC 可能少收一拍 | 按"停机即 0"语义确认 |
| `EAID` 与帧号不对应 | 合片错配 | 合片只认帧号，EAID 仅显示 |
| CSV 单写入线程 | 高频写入可能积压 | 与本次改造无关，单独观察 |

回归必测：
1. 激光模切：启动/停止、判定、回传、仿真界面、工具条按钮。
2. 五金：正常跑片、下线超前、下线滞后（少触发一次，须出提示、帧号回到 `Expected`、
   PLC 收到一条钳位 NG）、50ms 内重复触发、断网、换卷、复位、裁图异常。
3. 仿真：0/500/2500 时序、两工位界面数值与实际队列一致。
