# 机型与配置

面向现场工程师/开发者：机型怎么定、配置文件放哪、换机型怎么操作、缺配置是什么症状。

## 1. 机型由什么决定

唯一来源是 `ZSystemConfigurationFile\SystemParam.json` 的 `CraftType`：

| 值 | 机型 | 相机路数 |
|---|---|---|
| 0 | 激光模切一体机 | 6（0/1 模切、2 纠偏、3~5 尺寸） |
| 1 | 五金模切 | 5（0/1 模切、2~4 尺寸） |

启动时读取一次，之后运行期不可切换——工艺界面里没有机型下拉，双击配方也只会切配方。

机型决定了四样东西，所以不能中途改：

- 设备画像（相机角色、流程清单、设备业务类）
- 配方目录 `ZFormulaFile\＜机型＞\`
- 机型层配置目录 `ZSystemConfigurationFile\＜机型＞\`
- PLC 参数（激光走 D 寄存器表，五金走 CIP 符号表）

### 1.1 运行模式（`RunMode`，同一份文件）

`SystemParam.json` 里还有 `RunMode`，决定这台机器跑真机还是仿真：

| 值 | 模式 | 表现 |
|---|---|---|
| 0 | 自动（真机） | 连真实相机/PLC，工具栏显示「自动」 |
| 1 | 仿真 | 进程内 `SimCamera` + 本地 PLC 服务端，工具栏显示「仿真」，多出「仿真」菜单 |

```json
{ "CraftType": 0, "RunMode": 0 }
```

- 只在启动时读一次，运行期不能切；改完必须重启；
- 老文件没有该字段 → 反序列化得到 `0`，升级后仍是自动模式，不会被误切进仿真；
- 构建时 `build\copy-machine-config.ps1` 会把仓库里的 `CraftType` 与 `RunMode` 同步进输出目录那份
  `SystemParam.json`：缺 `RunMode` 键就补上，值不同就改掉，其它字段（机台号、账号）原样保留；
- 输出栏会打印 `[config] CraftType=…` / `[config] RunMode=… (Auto|Simulation)`，据此确认本次跑哪种模式；
- 仿真自身的参数（产能、端口、数据目录）不在这里，在 `ZSystemConfigurationFile\SimulationParam.json`。

## 2. 配置分三层

```
ZSystemConfigurationFile\
  SystemParam.json            ┐
  UserParam.xml               │ 通用层：与机型无关，换机型不动
  ControlCordParam.json       ┘
  激光模切一体机\              ┐
    AllCamParam.json          │ 机型层：一套机型一份，按 CraftType 选用
    AllLightControllerParam.json
    ImageSaveParamer.json     │
    PointInspectionParamer.json
    PLCDevParamr.json         ┘
  五金模切\
    AllCamParam.json
    AllLightControllerParam.json
    ImageSaveParamer.json
    PointInspectionParamer.json
    PLCDevParamr.json         ← 五金是 CIP 符号表，与激光的 D 寄存器表是两份数据
  CalibrationPlateParam*.xml  ┐
  CheckerboardParam*.xml      │ 机器层：只对这台机器的这组相机有效
  PretargetingCalibParam*.xml │ 不进 config，不跨机复制
  Msa* / CameraParam*         ┘
```

**判定标准**：这台机器换成同型号的另一台，文件内容还成立吗？

- 成立（账号、机型开关）→ 通用层
- 换机型就不成立（相机布局、光源映射、点检项、PLC 协议与地址表）→ 机型层
- 只对这一台机器成立（标定、相机 SN/IP）→ 机器层，永远不复制

## 3. 首次装机

编译就会自动投放配置（`CopyMachineConfig` 目标，Debug/Release 都生效）：

1. 改 `config\General\SystemParam.json` 的 `CraftType` 为目标机型；
2. 编译；
3. 构建脚本读 `CraftType`，把 `config\General\*` 投到 `ZSystemConfigurationFile\` 根下，
   把 `config\<机型>\*` 投到 `ZSystemConfigurationFile\<机型>\`；
4. 启动。

机型名映射在 `build\machine-types.txt`（`0=激光模切一体机`、`1=五金模切`），
新增机型只需在这里加一行并在 `config\` 下建同名目录。

投放只覆盖 `config\` 里存在的文件，且**目标已存在就跳过**：
输出目录里的参数不会被编译覆盖。要强制刷新，删掉输出目录里的对应文件再编译。

## 4. 换机型

1. **退出程序**（运行中改配置不会被感知）；
2. 改 `config\General\SystemParam.json` 的 `CraftType`，`RecipeName` 改成该机型下真实存在的配方；
3. 重新编译（构建会把目标机型的配置投放到输出目录）；
4. 启动。

手工操作也可以：直接从 `config\` 拷到输出目录，效果与编译投放一致。

配方不会自动跨机型迁移：`ZFormulaFile\激光模切一体机\77` 和 `ZFormulaFile\五金模切\77` 是两份独立数据。目标机型下没有该配方时，程序会按默认结构生成一份空配方。

## 5. 缺配置的症状对照

| 现象 | 缺的是 | 处理 |
|---|---|---|
| 登录提示“用户不存在” | `UserParam.xml` 只有内置 admin | 拷 `config\General\UserParam.xml` |
| 启动报流程名非法/为空 | `AllCamParam.json` 无相机或相机名重复 | 拷 `config\＜机型＞\AllCamParam.json` |
| 机型不对 | `SystemParam.json` 的 `CraftType` | 改值后重启 |
| 工艺参数页全空 | 该配方文件缺失或损坏（损坏会留 `.bak`） | 重新配置并保存 |

## 6. `config/` 与构建的关系

`config/` 不是源码，但构建会读它：`CopyMachineConfig` 目标在 Build 之后调用
`build\copy-machine-config.ps1`，按 `SystemParam.json` 的 `CraftType` 只投放**当前机型**那一套。

这样做的取舍：

- 优点：换机型只改一个值再编译，输出目录不会出现“别的机型的配置”；
- **只补缺失，不覆盖**：输出目录里的同名文件保持不动（`MachineNumber`、PLC IP、账号表都安全）。
  想强制刷新某个文件，删掉输出目录里的它再编译即可。

标定等机器级参数不在 `config/` 里，构建不会触碰。

运行期没有任何“从种子恢复”的入口，缺失文件的兜底只有一条：`Init()` 生成默认值并立即落盘。
所以第一次启动不会留下空壳文件，缺什么都能在磁盘上直接看出来。

## 8. 缺陷检测模型（全局一份，不随机型）

机型在出厂时确定、之后不切换，因此缺陷检测模型只有一份，放在输出根目录，不按机型分。

构建把 `config/AiModels/` 下的正负极**两份都**投放到输出目录：

```
config/AiModels/正极/model.onnx  → <OutDir>\AIModel\正极\model.onnx
config/AiModels/负极/model.onnx  → <OutDir>\AIModel\负极\model.onnx
```

运行期由配方的产品极性决定读哪一份（`Plugin.MQDefects` 按 `com_Cathode` 拼路径），因此**切换极性不需要重新编译**。

产品极性是配方的属性，在工艺界面「基础设置」里可改，保存后写入配方文件。`SystemParam.json` 不再有极性字段——它只负责机型（`CraftType`）。

### 需要成套备份的三样东西

| 文件 | 作用 | 缺失表现 |
|---|---|---|
| `AIModel\model.onnx` | `Plugin.MQDefects` 的分类模型 | `InitClassifierfinish=false`，分类功能静默不可用 |
| `Config\Plugin.DefectCoat\FeatureRuleClassifierConfig.json` | 特征规则 | 回退到内置默认规则，缺陷判定口径与现场不符 |
| `Config\Plugin.DefectCoat\FeatureRuleClassifier.AiClassifier.json` | 模型路径与阈值 | 模型路径为空 → AI 分类器不初始化 |
| `Config\Plugin.DefectCoat\FeatureRuleClassifier.ModelClassifier.json` | 传统分类器模型与标签 | 传统分类器不初始化 |

只备份 `.onnx` 而漏掉 JSON，等于模型换了但阈值、类别映射、标签顺序还是旧的。

### 配置里的模型路径要写相对路径

`DefectCoatObj.InitObj()` 通过 `DefaultConfigPathService.ResolvePath` 解析：

- 相对路径 → 相对软件根目录（**推荐**，写 `AIModel\model.onnx`）；
- 绝对路径 → 原样使用（兼容老现场配置）。

写绝对路径的配置拷到另一台机器会指向不存在的文件，必须现场重新用对话框选一次模型。

### 迁移到另一台机器

1. 退出程序；
2. 把源机器的 `AIModel\` 和 `Config\Plugin.DefectCoat\` 拷进本仓库的 `config\Assets\` 对应位置；
3. 检查 JSON 里的 `ModelPath` 是否相对路径，不是则改为 `AIModel\xxx.onnx`；
4. 编译（构建会把缺失的投放到输出目录）；
5. 启动，在缺陷检测界面确认分类器已初始化。
